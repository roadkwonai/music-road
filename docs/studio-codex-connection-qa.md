# 제작실·Codex 동일 대화 연결 검증

검증일: 2026-10-20 KST. 대상은 사용자가 연결 시험을 요청한 현재 Codex 데스크톱 대화다. 다른 대화를 만들거나 재개하지 않았다. 대화 ID·로컬 인증값은 이 문서에 저장하지 않는다.

## 판정

**앱 내부 전송과 공식 CLI 대기열의 동일 대화 실제 수신이 모두 성공했다.** `rm-queue-20261020-c`는 제출 당시 활성 턴이 끝난 뒤 같은 대화의 새 사용자 턴으로 도착했다. 이 확인 뒤 사용자가 설계대로 구현을 승인했다. HTML은 이 큐 경로를 사용하며 직접 App Server 소켓 연결은 필요 조건이 아니다.

| 검사 | 실제 관측 | 판정 |
| --- | --- | --- |
| 현재 대화 확인 | 앱의 `read_thread`로 현재 실행 대화 ID·작업 경로·진행 중 턴 일치 확인 | 성공 |
| 앱 내부 메시지 | `send_message_to_thread`에 현재 대화 ID와 진단 표식 전달. 도구 응답 뒤 같은 실행 문맥에 `codex_delegation` 메시지가 실제 도착 | 성공 |
| 기본 App Server 제어 연결 | `app-server daemon version` 실패. 기본 control socket 파일이 존재하지 않음 | 사용 불가 |
| 실행 중인 데스크톱 App Server 외부 Unix 연결 | 프로세스 실행 인자에서 `app-server` 확인, 외부 listen 인자·명명된 Unix 소켓은 확인되지 않음 | 외부 endpoint 미확인 |
| 공식 `codex queue` 기본 경로 | 같은 대화 UUID로 1회 제출. 종료 코드 0, `Queued message … for thread …` 응답과 메시지 ID 확인. 별도 App Server 프로세스 추가 없음 | 큐 등록 성공 |
| CLI 대기열의 동일 대화 수신 | 이전 응답 종료 뒤 진단 표식이 같은 대화 ID·작업 경로의 새 사용자 턴에 실제 도착했음을 앱 조회로 확인 | 성공: 다음 턴 처리 |
| 구현한 HTML 요청의 실제 수신·ACK | 가사 검토 요청이 같은 대화의 다음 사용자 턴으로 도착. 연결 ID·스냅샷·미디어 해시·구간·수정 가사·보존 조건 대조 후 공개 CLI `accepted → reviewing → succeeded` 기록 | 성공 |
| HTML 최종 상태와 복귀 | Ego에서 `검토 완료(음원·영상 변경 아님)`·읽기 전용 원가사 보존 확인 후 원래 제작실로 이동 | 성공 |

앱 내부 진단 표식은 `rm-native-20261020-b`, CLI 대기열 진단 표식은 `rm-queue-20261020-c`다. 메시지는 파일 수정·음원 생성·설치 없이 수신만 확인하는 내용이다. CLI 대기열에 같은 메시지를 반복 제출하지 않았다.

검증한 전역 CLI는 `0.163.0`, 앱이 제공한 실행 파일은 `0.163.0-alpha.10.2`다. 두 실행 파일 모두 `queue --help`를 제공한다. 버전 차이만으로 수신 실패의 원인을 확정하거나 앱·CLI를 업데이트하지 않는다.

## 지원 경로와 관측의 구분

공식 [Developer commands](https://learn.chatgpt.com/docs/developer-commands#codex-queue)는 기존 세션 UUID에 텍스트를 넣는 `codex queue --thread <UUID> --message <TEXT>`를 지원한다. 이번 시험은 이 명령의 기본 경로를 사용했다. 명령 종료 성공은 대기열에 기록됐다는 증거이며, 데스크톱 활성 턴에 즉시 전달됐다는 증거는 아니다.

공식 [App Server](https://developers.openai.com/codex/app-server)는 초기화·대화 조회와 `turn/start`·`turn/steer`를 제공한다. 그러나 그 API를 사용할 현재 대화 소유 서버의 외부 endpoint를 이번 검사에서 확인하지 못했다. 새 서버를 띄우거나 별도 `exec resume`을 실행해 같은 대화를 중복 소유하는 방법으로 대체하지 않았다.

앱 내부 전송 도구의 실제 수신은 확인했지만, 그 도구를 일반 HTML 서버에서 호출할 공개 연결 경로는 이번 검증에서 확인되지 않았다. 내부 pipe·DB·대화 파일을 역공학하거나 조작하는 연결은 만들지 않았다.

## 다음 관문

1. 확인된 큐 경로를 `현재 작업 후 진행`으로 구현한다. 즉시 `turn/steer`와 동일하게 표시하지 않는다. 요청 ID·CLI 메시지 ID와 `queued` 상태를 보존하고 실제 수신 ACK를 별도로 연결한다.
2. HTML → 로컬 서버 → 공식 큐 → 같은 대화 → 공개 CLI ACK → HTML 상태 조회를 검토 전용 요청으로 검증했다. 음악·영상 재생성은 이 시험에 포함하지 않았다. 프로젝트 스냅샷과 원음·원가사·영상 해시는 유지됐다.
3. 향후 즉시 활성 턴에 입력하는 기능이 필요하면 해당 대화 소유 서버의 지원 endpoint를 별도로 검증한다. 기존 native 도구의 성공만으로 외부 즉시 제어 기능을 구현 완료로 표시하지 않는다.
4. 연결되지 않은 요청을 `accepted`·`running`·`succeeded`로 표시하거나 큐 응답만으로 실제 음악 생성을 시작하지 않는다.

## 변경·검증 범위

연결 진단 단계에서는 문서만 보완해 기존 395개 회귀 검사를 반복하지 않았다. 이후 실제 수신을 확인하고 사용자의 구현 승인을 받아 제품 구현을 진행한다. 구현 검증 결과는 [CLI 검수 기록](cli-qa-report.md)에 추가한다. 실제 음원 생성·모델 설치·앱 재시작·데몬 시작·Release 변경은 연결 시험에서 수행하지 않았다.
